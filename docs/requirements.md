# ウマ娘 総獲得ファン数トラッカー 要件定義書

- 状態: ドラフト(確認事項の回答待ち)
- 作成日: 2026-10-07

## 1. 目的・背景

ウマ娘 プリティーダービーのクラブ/サークル画面などに表示される「総獲得ファン数」を、スクリーンショットから自動で読み取り、日毎の増加量(日次ファン獲得数)を統計としてまとめる。
手入力の手間と転記ミスをなくし、成長の推移を継続的に把握できるようにする。

## 2. スコープ

### 2.1 対象(In Scope)

- スクリーンショット画像から「総獲得ファン数」の数値を抽出する
- 抽出した数値を日付と紐づけて保存する
- 日毎の増加量(前日差)を算出し、一覧・グラフで表示する
- 抽出結果の目視確認・手動修正
- 統計データのエクスポート(CSV)

### 2.2 対象外(Out of Scope / 初期リリース)

- ゲームクライアントへの接続、通信の解析、ゲームデータの自動取得(規約上のリスクがあるため行わない)
- スクリーンショットの自動撮影・自動アップロード
- 複数ユーザー間のランキング・共有機能
- ファン数以外の指標(育成結果、ガチャ履歴など)の集計

## 3. 想定ユーザー・利用シーン

- 想定ユーザー: ウマ娘をプレイする個人(まずは作成者本人)
- 利用シーン: 毎日1回(または随時)ゲーム内のファン数表示をスクリーンショットし、ツールに取り込んで日次推移を確認する

## 4. 機能要件

### 4.1 画像取り込み(FR-1)

| ID | 要件 | 優先度 |
|----|------|--------|
| FR-1.1 | PNG / JPEG の画像ファイルを1枚以上選択して取り込める | 必須 |
| FR-1.2 | フォルダ指定による一括取り込みができる | 必須 |
| FR-1.3 | ドラッグ&ドロップ/クリップボード貼り付けに対応する | 任意 |
| FR-1.4 | 同一画像(ハッシュ一致)の二重取り込みを検出し、スキップまたは警告する | 必須 |

### 4.2 ファン数の抽出(FR-2)

| ID | 要件 | 優先度 |
|----|------|--------|
| FR-2.1 | 画像中の「総獲得ファン数」表示領域を特定し、数値(桁区切りカンマ付きの整数)を OCR で読み取る | 必須 |
| FR-2.2 | 画面の種類(対象画面)ごとにファン数の表示位置を設定として定義できる | 必須 |
| FR-2.3 | 画像の解像度・アスペクト比(スマホ縦持ち/PC版など)の違いに対応する | 必須 |
| FR-2.4 | 読み取りの信頼度を算出し、低信頼度の結果を「要確認」として区別する | 必須 |
| FR-2.5 | 対象画面でない画像・数値が読めない画像はエラーとして扱い、他の画像の処理は継続する | 必須 |
| FR-2.6 | 前回値より減少している、または極端に増加している値を異常値として警告する | 必須 |

### 4.3 日付の決定(FR-3)

| ID | 要件 | 優先度 |
|----|------|--------|
| FR-3.1 | 撮影日時を、①画像の EXIF、②ファイル名(例: `Screenshot_20261007-...`)、③ファイル更新日時、の優先順で自動取得する | 必須 |
| FR-3.2 | 取り込み時に日付を手動で指定・修正できる | 必須 |
| FR-3.3 | 「1日の区切り」の時刻を設定できる(ゲームの日替わりは午前 4 時など。既定値は確認事項参照) | 必須 |
| FR-3.4 | 同一日に複数枚ある場合は、その日の最後(最新時刻)の値を日次値として採用する | 必須 |

### 4.4 データ管理(FR-4)

| ID | 要件 | 優先度 |
|----|------|--------|
| FR-4.1 | 抽出結果(日付、ファン数、元画像パス、信頼度、手動修正の有無)をローカルに永続化する | 必須 |
| FR-4.2 | 抽出結果を一覧表示し、値・日付の修正、レコード削除ができる | 必須 |
| FR-4.3 | 欠損日(スクリーンショットのない日)を明示する | 必須 |
| FR-4.4 | データ全体のバックアップ/復元(エクスポート/インポート)ができる | 任意 |

### 4.5 統計・可視化(FR-5)

| ID | 要件 | 優先度 |
|----|------|--------|
| FR-5.1 | 日毎の「総獲得ファン数」と「前日からの増加量」を表で表示する | 必須 |
| FR-5.2 | 欠損日をまたぐ場合、増加量は期間合計として扱い、日割り平均を併記する | 必須 |
| FR-5.3 | 総ファン数の推移(折れ線)と日次増加量(棒)をグラフ表示する | 必須 |
| FR-5.4 | 期間(直近7日/30日/任意範囲)で絞り込める | 必須 |
| FR-5.5 | 週次・月次の集計(合計、平均、最大)を表示する | 任意 |
| FR-5.6 | 統計表を CSV でエクスポートする | 必須 |

### 4.6 複数アカウント・複数対象(FR-6)

| ID | 要件 | 優先度 |
|----|------|--------|
| FR-6.1 | 複数のトレーナー(アカウント)を区別して管理できる | 確認事項次第 |
| FR-6.2 | 画像からトレーナー名・ID を読み取り、自動で振り分ける | 確認事項次第 |

## 5. 非機能要件

| 区分 | 要件 |
|------|------|
| 精度 | 対象画面の正常な画像に対し、ファン数の読み取り正答率 99% 以上を目標とする。誤読は FR-2.4 / FR-2.6 により検出し、手動修正で救済する |
| 性能 | 画像 1 枚あたり数秒以内、100 枚の一括取り込みを数分以内に処理する |
| プライバシー | 画像・データはローカルのみで処理・保存し、外部サービスへ送信しない(OCR もローカル実行) |
| 移植性 | 作成者の開発環境(Linux/WSL2)で動作し、利用環境(Windows 想定)でも動く構成とする |
| 保守性 | 画面ごとの読み取り領域は設定ファイルで定義し、ゲームの UI 変更時にコード変更なしで調整できる |
| テスト | 代表的なスクリーンショット(サンプル画像)を使った OCR の回帰テストを用意する |
| 規約 | ゲームのクライアントやサーバーには一切アクセスせず、ユーザー自身が撮影した画像のみを入力とする |

## 6. 提案する構成(たたき台)

実装方針は確認事項の回答後に確定する。現時点の案は次のとおり。

- 形態: ローカルで動く CLI + 簡易 Web UI(または CLI のみ)
- 言語: Python
- OCR: ローカル OCR エンジン(Tesseract / PaddleOCR / EasyOCR などから精度検証して選定)
- 画像前処理: 対象領域の切り出し、拡大、二値化(OpenCV / Pillow)
- 保存: SQLite(または CSV/JSON)
- 可視化: Web UI 上のグラフ(Chart.js 等)または matplotlib による画像出力

### 処理フロー

1. 画像取り込み(重複チェック)
2. 撮影日時の決定(EXIF → ファイル名 → 更新日時、日替わり時刻で補正)
3. 対象領域の切り出し・前処理
4. OCR によるファン数抽出と信頼度算出
5. 異常値検査(減少・急増)
6. 保存(要確認は確認キューへ)
7. 日次値の確定、前日差の算出、統計・グラフ表示

## 7. 受け入れ基準

- サンプルのスクリーンショット(複数日分)を取り込み、日毎のファン数と増加量が表に出力される
- 同一画像の再取り込みで重複登録されない
- 読み取り失敗・低信頼度の画像が一覧で識別でき、手動修正後に統計へ反映される
- 欠損日がある期間でも、増加量が誤って 1 日分として計上されない
- CSV エクスポートの値が画面表示と一致する

## 8. 確認事項

回答を受けて本書を更新する。

1. **「総獲得ファン数」の対象**: どの画面の数値を指すか(トレーナー情報、サークル、育成ウマ娘ごとなど)。対象画面のサンプルスクリーンショットを数枚いただけるか。
2. **プレイ環境**: スマホ(Android / iOS)か PC 版(DMM)か。スクリーンショットの解像度・縦横の種類は何種類あるか。
3. **日替わり時刻**: 日付の区切りはゲームの日替わり(午前 4 時など)に合わせるか、0 時にするか。
4. **撮影頻度**: 1 日 1 枚か、1 日に複数枚か。過去分のまとめ取り込みはあるか(あれば何枚程度か)。
5. **アカウント数**: 1 アカウントだけか、複数アカウントを区別して管理したいか。
6. **利用形態**: CLI のみ、ローカル Web UI、デスクトップアプリのどれを希望するか。
7. **技術選定**: Python + ローカル OCR(外部送信なし)で問題ないか。使いたい言語や避けたい技術はあるか。
8. **出力**: 表・グラフ・CSV のうち必須のものはどれか。Excel / スプレッドシートへの連携は必要か。
9. **異常値の扱い**: ファン数が前回より減ったときの扱い(エラー扱い/警告のみ)や、急増とみなす閾値に希望はあるか。
10. **公開範囲**: 個人利用のみか、他のプレイヤーにも配布する可能性があるか(配布する場合は UI 言語や導入のしやすさの要件が増える)。
